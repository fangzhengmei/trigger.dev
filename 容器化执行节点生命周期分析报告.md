### 4.2 任务重入队 (NACK)

**NACK 流程** (`internal-packages/run-engine/src/run-queue/index.ts`)
```typescript
// 当心跳超时或节点掉线时
async nackMessage(messageId: string): Promise<boolean> {
  // 1. 解锁任务
  await this.runLock.unlock([messageId]);
  
  // 2. 将消息从处理队列移回待处理队列
  // 3. 增加 nack 计数（防止无限重试）
  const nackCount = await this.incrementNackCounter(messageId);
  
  // 4. 超过最大 nack 次数则移至死信队列
  if (nackCount > this.maximumNackCount) {
    await this.moveToDeadLetterQueue(messageId);
    return false;
  }
  
  // 5. 重新入队
  await this.requeueMessage(messageId);
  return true;
}
```

### 4.3 状态机处理

**心跳失败时的状态转换** (`taskRunHeartbeatFailed.server.ts:51-155`)

| 当前状态 | 处理方式 | 原因 |
|---------|----------|------|
| `PENDING` / `DEQUEUED` / `WAITING_TO_RESUME` / `PAUSED` | NACK 重新入队 | 任务未开始执行，可安全重试 |
| `EXECUTING` / `RETRYING_AFTER_FAILURE` | 标记失败 | 执行中掉线可能已产生副作用，避免重复执行 |
| `DELAYED` / `PENDING_VERSION` / `WAITING_FOR_DEPLOY` | ACK 后重新调度 | 等待状态，由专门系统处理 |
| 终态（`COMPLETED_*`/`CANCELED` 等） | ACK 忽略 | 任务已完成，发送取消信号给残留容器 |

```typescript
async enqueueRunsForBackgroundWorker(backgroundWorkerId: string) {
  // 批量处理，防止一次处理过多
  const maxCount = this.options.queueRunsPendingVersionBatchSize ?? 200;
  
  const pendingRuns = await this.$.readOnlyPrisma.taskRun.findMany({
    where: { status: "PENDING_VERSION", /* 匹配新版本 */ },
    orderBy: { createdAt: "asc" },
    take: maxCount + 1, // 多取一条判断是否还有更多
  });
  
  for (const run of pendingRuns.slice(0, maxCount)) {
    await this.$.prisma.$transaction(async (tx) => {
      // 1. 更新状态为 PENDING
      const updatedRun = await tx.taskRun.update({
        where: { id: run.id },
        data: { status: "PENDING" },
      });
      // 2. 正常入队
      await this.enqueueSystem.enqueueRun({ run: updatedRun, ... });
    });
  }
  
  // 还有更多，继续调度
  if (pendingRuns.length > maxCount) {
    await this.scheduleResolvePendingVersionRuns(backgroundWorkerId);
  }
}
```

## 10. 节点掉线任务接管端到端链路详解

### 10.1 触发条件与检测链路

#### 10.1.1 心跳丢失检测流程

**触发源：任务级心跳超时**

```
任务执行中
    ↓
任务心跳开始 (VisibilityTimeout.startHeartbeat)
    ↓
Graphile Worker 调度 TaskRunHeartbeatFailed 任务
    ├─ 正常路径：Worker 定期 heartbeat() → 重新调度 TaskRunHeartbeatFailed（重置倒计时）
    └─ 超时路径：到达超时时间 → 触发 TaskRunHeartbeatFailedService.call()
```

**关键代码路径** (`apps/webapp/app/v3/marqs/v3VisibilityTimeout.server.ts:1-39
```typescript
// 开始心跳时调度一个超时任务
async startHeartbeat(messageId: string, timeoutInMs: number) {
  await TaskRunHeartbeatFailedService.enqueue(
    messageId, 
    new Date(Date.now() + timeoutInMs)
  );
}

// 每次心跳重新调度（本质是删除旧任务，创建新任务
async heartbeat(messageId: string, timeoutInMs: number) {
  await TaskRunHeartbeatFailedService.dequeue(messageId);
  await TaskRunHeartbeatFailedService.enqueue(
    messageId, 
    new Date(Date.now() + timeoutInMs)
  );
}
```

#### 10.1.2 三层检测机制的协作

| 检测层级 | 触发时机 | 响应延迟 | 处理范围 |
|---------|----------|----------|----------|
| **任务级心跳 | 任务执行中每 X 秒 | 较短（如 30s） | 单个任务 |
| **节点级心跳 | 心跳 | 节点每 Y 秒 | 较长（如 60s） | 节点上所有任务 |
| **K8s Pod 监听 | Pod 状态变更 | 几乎实时 | Pod 级故障 |

### 10.2 状态机详细转换链路

```typescript
public async nackMessage({
  orgId,
  messageId,
  retryAt,
  incrementAttemptCount = true,
  skipDequeueProcessing = false,
}: {
  orgId: string;
  messageId: string;
  retryAt?: number;
  incrementAttemptCount?: boolean;
  skipDequeueProcessing?: boolean;
}) {

  // 1. 读取消息
  const message = await this.readMessage(orgId, messageId);

      availableAt: new Date(Date.now() + 500),
```

```typescript
  // 1. 查询 PENDING_VERSION 的任务
  const pendingRuns = await this.$.readOnlyPrisma.taskRun.findMany({
```

| 触发事件 | 处理方式 | 新状态 | 原因 |
|---------|----------|---------|------|
| **新任务入队，无匹配 Worker** | 设置 PENDING_VERSION | PENDING_VERSION | 等待新版本部署 |
| **部署完成** | 批量处理 PENDING_VERSION | PENDING | 新版本就绪，进入队列 |
| **出队时版本不匹配** | 重新设置 PENDING_VERSION | PENDING_VERSION | 任务不在最新版本 |
| **出队时 Worker 不匹配** | NACK 重新入队 | PENDING | Worker 版本不匹配 |
| **出队成功** | 锁定版本 | DEQUEUED | 锁定到特定版本 |

### 12.3 锁的作用总结

| 锁类型 | 作用场景 | 保护目标 |
|---------|----------|----------|
| **RunLocker 分布式锁 | 出队/NACK/ACK | 防止并发修改同一任务 |
| **并发集合锁** | 出队/NACK | 环境/队列并发控制 |
| **版本锁定 (lockedToVersionId) | 出队后 | 确保任务始终在同一版本执行 |
| **队列锁定 (lockedQueueId) | 出队后 | 确保任务始终在同一队列执行 |
| **计数器 TTL | 滚动发布期间 | 限制 v1/v2 重叠漂移 |

## 13. Socket 断开与心跳超时双路径时序分析

### 13.1 核心发现：Socket 断开不直接触发任务接管

经过代码追踪，**Socket 断开事件本身并不直接触发任务状态变更或接管流程**。Socket 断开仅做清理工作（取消事件监听、停止定时器），真正的任务接管完全依赖心跳超时路径。

这一设计是刻意的：Socket 断开可能是瞬时网络抖动导致的短暂重连，不应立即判定节点死亡。心跳超时提供了更可靠的检测窗口。

### 13.3 双路径汇聚分析

#### 13.3.1 汇聚点

**Socket 断开与心跳超时的唯一汇聚点是心跳超时触发后的 `TaskRunHeartbeatFailedService.call()`**。

```
Socket 断开                    心跳超时
     │                            │
     │ (仅清理监听器/定时器)        │ (实际触发任务状态变更)
     │                            │
     ▼                            ▼
  心跳停止发送 ──────────────→ 心跳超时到期
                                    │
                                    ▼
                          TaskRunHeartbeatFailedService.call()
                          (apps/webapp/app/v3/taskRunHeartbeatFailed.server.ts:13)
                                    │
                                    ▼
                              按状态分支处理
```

Socket 断开只是**间接**导致心跳停止发送，真正的接管决策完全由心跳超时机制驱动。

#### 13.3.2 时序关系

```
时间轴：
T0: 节点故障/网络断开
    │
    ├── [立即] Socket.IO 检测到连接断开
    │   → "disconnect" 事件触发
    │   → 清理 Socket 监听器、停止 SharedQueueConsumerPool
    │   → ⚠️ 无任务状态变更
    │
    ├── [T0 → T0+visibilityTimeoutInMs] 心跳停止但超时未到期
    │   → V3GraphileVisibilityTimeout 正在等待
    │   → 任务仍在原节点"持有"状态
    │   → 此窗口期内的任务无法被新节点接管
    │
    └── [T0+visibilityTimeoutInMs] 心跳超时到期
        → Graphile Worker 执行 TaskRunHeartbeatFailedService.call()
        → 根据任务状态执行 NACK/ACK/失败标记
        → 新节点可开始接管
```

**默认超时配置** (`apps/webapp/app/env.server.ts:602-605`)：
```typescript
MARQS_VISIBILITY_TIMEOUT_MS: z.coerce.number().int().default(60 * 1000 * 15),
// 默认: 900,000ms = 15 分钟
```

**这意味着从节点故障到新节点接管，最坏情况下需等待 15 分钟。**

### 13.5 额外路径：RUN_CRASHED 事件

除了 Socket 断开和心跳超时外，还存在一条**主动崩溃上报路径**：

```
Worker 进程异常退出
    │
    ├── Pod 内 Coordinator 检测到异常
    │   apps/coordinator/src/index.ts:453-465
    │   → crashRun() → 发送 "RUN_CRASHED" 到 Platform
    │
    └── Provider 命名空间接收 RUN_CRASHED
        apps/webapp/app/v3/handleSocketIo.server.ts:392-404
        → CrashTaskRunService.call()
        → 判断 isCrashableRunStatus
        → FailedTaskRunRetryHelper → 尝试重试
        → 重试失败 → FinalizeTaskRunService (标记 CRASHED)
```

**关键代码** — `crashTaskRun.server.ts:23-120`：
```typescript
export class CrashTaskRunService extends BaseService {
  public async call(runId: string, options?: CrashTaskRunServiceOptions) {
    // 1. 检查任务是否在可崩溃状态
    if (!isCrashableRunStatus(taskRun.status)) return;

    // 2. 尝试重试
    const retryResult = await retryHelper.call({
      runId,
      completion: { ok: false, error: { ... } },
      isCrash: true,
    });

    // 3. 重试成功则直接返回
    if (retryResult === "RETRIED") return;

    // 4. 重试失败，标记为 CRASHED
    await finalizeService.call({ status: "CRASHED", ... });
  }
}
```

**与心跳超时的区别：**
- `RUN_CRASHED` 是**主动上报**，延迟极低
- 心跳超时是**被动检测**，需等待 visibilityTimeout 窗口
- `RUN_CRASHED` 走 `CrashTaskRunService`，有重试逻辑
- 心跳超时走 `TaskRunHeartbeatFailedService`，按状态分支处理

### 13.6 三条路径完整对比

| 特性 | Socket 断开 | 心跳超时 | RUN_CRASHED |
|------|-----------|---------|-------------|
| **触发源** | 网络断开/节点下线 | visibilityTimeout 到期 | Worker 进程异常 |
| **检测延迟** | 秒级 | 15 分钟（默认） | 秒级 |
| **触发任务状态变更** | ❌ 否 | ✅ 是 | ✅ 是 |
| **处理服务** | 无 | `TaskRunHeartbeatFailedService` | `CrashTaskRunService` |
| **能否触发重试** | ❌ 间接 | ✅ 按状态 | ✅ 有重试逻辑 |
| **最终汇聚点** | → 心跳超时 | `marqs.nackMessage()` / `FailedTaskRunService` | `FinalizeTaskRunService` |
| **适用场景** | 所有断连 | 所有无心跳场景 | 仅 Pod 内可检测的崩溃 |

### 13.9 设计哲学总结

1. **Socket 断开仅做资源清理，不做业务决策** — 避免网络抖动导致的误判
2. **心跳超时是唯一可靠的故障检测器** — 通过超时窗口容忍短暂断连
3. **默认 15 分钟超时窗口是权衡值** — 足够长以容忍瞬时故障，足够短以避免任务长期悬挂
4. **RUN_CRASHED 作为快速路径补充** — 在 Coordinator 存活时可秒级感知崩溃
5. **所有路径最终汇聚于状态判断** — `TaskRunHeartbeatFailedService` 是唯一的任务接管决策点

## 14. 崩溃上报与心跳超时并发处理详解

### 14.1 并发场景分析

同一运行实例（run）可能同时触发多条故障处理路径，典型并发场景：

```
T0: Worker 进程崩溃
    │
    ├── [T0+1s] Coordinator 检测到异常
    │   → 发送 RUN_CRASHED 事件到 Platform
    │   → CrashTaskRunService.call(runId)
    │
    └── [T0+900s] 心跳超时到期
        → TaskRunHeartbeatFailedService.call(runId)
```

如果 CrashTaskRunService 在 900s 内完成了任务状态处理，则心跳超时路径会因状态检查而中断。否则两条路径会并发执行，需要多层防护机制避免重复写入和重复入队。

### 14.2 isCrashableRunStatus 状态拦截机制

#### 14.2.1 状态定义

**代码位置**：`apps/webapp/app/v3/taskStatus.ts:71,108-110`

```typescript
export const CRASHABLE_RUN_STATUSES = NON_FINAL_RUN_STATUSES;

export function isCrashableRunStatus(status: TaskRunStatus): boolean {
  return CRASHABLE_RUN_STATUSES.includes(status);
}
```

其中 `NON_FINAL_RUN_STATUSES` 包含：
- `DELAYED` - 延迟执行中
- `PENDING` - 待执行
- `PENDING_VERSION` - 等待新版本
- `WAITING_FOR_DEPLOY` - 等待部署
- `DEQUEUED` - 已出队待执行
- `EXECUTING` - 执行中
- `WAITING_TO_RESUME` - 等待恢复
- `RETRYING_AFTER_FAILURE` - 失败后重试中
- `PAUSED` - 暂停

#### 14.2.2 拦截点

**CrashTaskRunService 入口检查** (`crashTaskRun.server.ts:50-56`)：
```typescript

    runId, status: taskRun.status,

  return;  // ⚠️ 直接返回，中断流程
}
```

**FailedTaskRunService 入口检查** (`failedTaskRun.server.ts:56-63`)：

```typescript
    taskRun, completion,

  return;  // ⚠️ 直接返回，中断流程
}
```

**CompleteAttemptService 中间检查** (`completeAttempt.server.ts:109-120`)：

#### 14.4.2 第二层：消息队列层面防护

**marqs.acknowledgeMessage()** (`marqs/index.server.ts:1057-1113`)：
```typescript
public async acknowledgeMessage(messageId: string, reason: string = "unknown") {
  const message = await this.readMessage(messageId);

  if (!message) {
    logger.log(`[${this.name}].acknowledgeMessage() message not found`, {
      messageId, service: this.name, reason,
    });
    return;  // ⚠️ 消息已不存在，中断流程

  await this.options.visibilityTimeoutStrategy.cancelHeartbeat(messageId);
  await this.#callAcknowledgeMessage({ /* Redis Lua 原子操作 */ });
}
```

**marqs.nackMessage()** (`marqs/index.server.ts:1119-1186`)：
```typescript
public async nackMessage(messageId: string, retryAt: number = Date.now()) {
  const message = await this.readMessage(messageId);

  if (!message) {
    logger.debug(`[${this.name}].nackMessage() message not found`, { messageId, ... });
    return false;  // ⚠️ 消息已不存在，中断流程
  }

  const nackCount = await this.#getNackCount(messageId);

  if (nackCount >= this.options.maximumNackCount) {
    // 超过最大 nack 次数，改为 ack 并返回 false
    await this.acknowledgeMessage(messageId, "maximum nack count reached");
    return false;
  }

  await this.options.visibilityTimeoutStrategy.cancelHeartbeat(messageId);
  await this.#callNackMessage(messageId, message, retryAt);
  return true;
}
```

**关键机制**：
1. `readMessage()` 检查消息是否存在 — 消息已被 ACK 则直接返回
2. `cancelHeartbeat()` 取消心跳超时调度 — 防止心跳超时路径再次触发
3. Redis Lua 脚本原子操作 — 保证队列操作的原子性

### 14.5 并发执行顺序与竞态分析

#### 14.5.1 正常时序（Crash 先于心跳超时）

```
T0: Worker 崩溃
T1: CrashTaskRunService.call() 开始

    ├── CompleteAttemptService.call()
    │   ├── isFinalRunStatus → 通过（非终态）
    │   ├── 不可重试 → FinalizeTaskRunService(CRASHED)
```

### 14.8 并发安全设计总结

1. **状态机驱动的分层防护** — 从入口到最终写入，每层都有状态检查
2. **先读后写的乐观锁模式** — 通过状态检查实现无锁并发控制
3. **消息队列的原子性保障** — Redis Lua 脚本确保队列操作的原子性
4. **jobKey 去重机制** — Graphile Worker 的 jobKey 防止重复调度
5. **终态不可变原则** — 一旦写入终态，所有路径都会安全中断
6. **心跳取消机制** — 任何 ACK/NACK 操作都会先取消心跳超时调度

这些机制共同确保了即使多条故障处理路径并发触发，也不会出现重复入队、重复状态写入或双重消费的问题。

## 7. 核心设计亮点

### 7.1 可靠性设计

1. **消费者池动态伸缩** - 基于队列长度的 EWMA 平滑算法

3. **并发控制** - 环境级、队列级、任务级多层并发限制
4. **冷却时间** - 伸缩操作的冷却时间防止频繁抖动

### 7.3 可观测性设计

1. **OpenTelemetry 集成** - 全链路追踪
2. **Prometheus 指标** - 队列长度、消费者数量、伸缩决策等
3. **结构化日志** - 所有关键操作都有详细日志
4. **事件总线** - 状态变更通过事件总线通知相关系统

## 9. 总结

Trigger.dev 容器化执行节点的生命周期管理体现了以下设计原则：

1. **分层抽象** - 通过 WorkloadManager、ResourceMonitor 等接口抹平底层编排平台差异
2. **可靠性优先** - 多层心跳、分布式锁、VisibilityTimeout、死信队列等机制确保任务不丢失
3. **版本安全** - PENDING_VERSION 状态、版本锁定、并发计数器 TTL 等机制防止滚动部署时的双重消费
4. **可观测性** - 全链路追踪、指标收集、结构化日志确保系统可观测
5. **弹性伸缩** - 基于队列长度的动态伸缩算法，结合冷却时间防止抖动

整体架构既保证了在不同运行环境（Docker/Kubernetes/Compute）下的一致性体验，又通过多层次的可靠性设计确保了任务执行的正确性和稳定性。
